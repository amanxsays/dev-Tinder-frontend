# Android 1.0.5 (code 6): SRi, smoother startup and saved chats

## Implemented

1. Shared accessible startup spinner, concise 12px status text and contrasting green Sign in instead. The update-check screen no longer focuses a bordered heading. Notification/session restoration uses authenticated GET /session, which does not wait for coding-statistics enrichment. The profile screen retains its separate stats refresh without replacing newer profile edits.
2. Assistant display name, fast greeting and generation identity are SRi. DevTinder remains the application brand.
3. Profile-photo chooser replaces the URL field. JPG/PNG/WebP up to 5 MB are uploaded directly using a short-lived authenticated Cloudinary signature; signed allowed formats and a 1024px limiting transformation apply. Backend completion verifies Cloudinary's response signature and the current user's avatar namespace before generating/storing the Cloudinary URL. Prior photo remains on failure. Unused uploads can remain as orphan assets; automatic avatar cleanup is not implemented. Resume behavior remains separate.
4. Android offers opt-in Save this account on my phone, followed on later visits by Continue as <email>. Credentials are encrypted in app-private Android Keystore-backed storage, excluded from backup, and retrieved only after the Android screen-lock challenge. There is one saved account; Remove saved account deletes it. Logout clears session/cached profile/chats but keeps explicitly saved credentials until removed. A secure screen lock is required; cancel or failure returns to manual login. Browser sign-in retains browser password-manager/autocomplete support; no web password vault is added. JWT lifetimes remain unchanged. Bridge logging is disabled to avoid logging sensitive plugin arguments even in debug builds.
5. Android caches the account profile, connections and bounded recent human-chat history in the encrypted native store. Cache reads/writes check the current unexpired local session and account ID. Logout, explicit session rejection and account switching invalidate cached access; account changes clear old cache. Up to 18 chat caches plus profile/connections are kept. Each cache is capped at 512,000 characters; each chat keeps up to 300 recent messages within a 450,000-character budget. Avatar/image binaries, PDFs, AI conversations and the entire application database are not cached.
6. Developer search results show Chat for confirmed accepted connections, including when entering search before visiting Connections. Existing profile links remain. Chat authorization remains server-side.

## Incremental chat sync

Mobile GET /chat/:targetUserId?sync=1 returns up to 300 recent messages. Subsequent requests include after=<last confirmed history message ID>, so only newer messages travel over the network. Canonical IDs deduplicate cache/history/live broadcasts/acknowledgements. A stale cursor explicitly resets recent history. Reconnect/focus/online refresh uses the cursor. Up to five batches are fetched per refresh; larger backlogs expose an explicit continue-sync action. Load earlier messages fetches an older page online, preserving access to earlier history. The embedded Mongo document is still read server-side; this change primarily reduces client transfer. No schema migration, delivery guarantees or automatic offline send queue is added.

## Offline limits and required updates

Read-only offline startup requires an unexpired saved native session, a cached profile and a version decision verified online within the last 24 hours. A known newer required build always blocks, including offline. After 24 hours without version verification, connect to check updates. This is the narrow adjustment to the earlier strict offline policy needed for the newly requested cached offline use; online checks still enforce the current required release.

Previously cached connections and chat text can be read offline. Sending messages, AI, signup/login, profile writes/uploads, uncached profiles/search/stats and PDF downloads need connectivity. Uncached pictures may be unavailable. The app labels offline/saved data, keeps drafts, makes no chat/backend requests in the tested cached offline flow and refreshes newer messages when online again. This is partial offline support, not a complete offline app.

## Final phone checks after signing/publishing

- Install 1.0.5 over 1.0.4; confirm version and retained login.
- Tap a real message notification: compact spinner then correct conversation; repeat after background/restart. Render cold-start/network delay can still occur.
- Save an account explicitly with phone screen lock configured. Logout, Continue as, cancel/unlock, sign in; remove saved account and verify the option disappears. Do not share credentials/PINs.
- Pick a real JPG/PNG/WebP; check avatar/profile/reload. Reject PDF/oversized files. Interrupt an upload; old photo stays.
- Visit Connections/chat online first, then airplane mode/restart and read cached text. Cannot send/ask SRi/upload offline. Go online and receive new messages without duplicate bubbles. Load an earlier page online.
- Search an accepted connection and a stranger: Chat only for the connection; profile links continue to work.
- Logout/account switch clears private caches. Expired login requires authentication. Required update cannot be skipped; old/no version lease requires network verification.

## Rollout

Deploy the compatible Node session/photo/sync routes, Spring SRi naming and frontend source. Build with the existing release key; inspect signed production code 6 and bundle markers. Only then publish the APK and update Netlify metadata/required version together. The download stays 1.0.4 while 1.0.5 is unsigned. No service URLs, production secrets, JWT lifetime or database collections are migrated. Reverting the additive source changes preserves old clients; for an installed APK fix publish a higher signed versionCode.
